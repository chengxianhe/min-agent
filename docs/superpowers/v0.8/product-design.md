# min-agent-demo V0.8 可观察的任务分解与顺序执行产品设计

## 版本定位

V0.8 的主题是“可观察的任务分解与顺序执行”。

V0.1–V0.7 已经验证了最小 Agent Loop、真实模型决策、多文件读取、过程解释、受控写文件、项目上下文和受控命令执行。当前 Agent 能围绕一个目标连续调用工具，但还不能明确展示：一个复合目标如何被拆成若干可验收任务、当前正在完成哪一个任务，以及前序结果如何推动整体计划前进。

V0.8 只增加这一层任务状态。它不是项目管理系统，也不是多 Agent 编排器。

## 最重要的产品效果

用户提出复合目标后，Agent 先生成一份可观察的任务清单，再逐项执行。每完成一步，都根据真实工具结果更新任务状态；首次失败或权限拒绝后停止计划，并明确展示已完成、失败和未执行的任务。

用户不仅能看到 Agent 调用了哪些工具，还能回答三个更高层的问题：

1. Agent 把我的目标拆成了哪些任务？
2. 当前工具调用属于哪个任务？
3. 整体目标为什么完成、失败或停在这里？

## 核心演示场景

用户输入：

```text
阅读 workspace 中的项目资料，获取当前时间，并生成一份带时间的 summary.md。
```

Agent 在首次工具调用前生成固定计划：

1. 查看 workspace 中可用的项目文件。
2. 读取并整理相关项目资料。
3. 获取当前本地时间。
4. 生成并写入 `summary.md`。

这个场景复用前面版本已经验证的能力：

- `list_dir` 和 `read_file`：V0.3 多文件上下文。
- `write_file` 和权限确认：V0.5 可控写文件。
- 项目上下文与工具目录：V0.6 上下文注入。
- `run_command/get_current_time` 和权限确认：V0.7 可控命令执行。

V0.8 的新增价值不是再增加工具，而是让这些能力服务于一份显式、可观察的任务计划。

## 简单目标与复合目标

### 简单目标

简单目标只包含一个可验收结果，不生成任务计划栏，页面和执行结构保持 V0.7 现状。

例如：

```text
现在几点？
```

即使内部调用一次 `run_command`，它仍然只有一个可验收目标。

再例如：

```text
总结整个 workspace。
```

它可能调用一次 `list_dir` 和多次 `read_file`，但这些工具调用共同服务于一个“完成资料总结”的结果，仍然可以作为简单目标执行。

### 复合目标

复合目标包含 2–5 个有明确先后关系、可分别验收的子目标。只有这类运行才生成任务计划并展示任务计划栏。

工具调用数量不能作为是否分解任务的判断依据。任务是用户结果层的子目标，不是 TraceEvent 或工具调用的另一种名称。

## 任务模型

每个任务至少包含：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 运行内稳定标识，例如 `task-1` |
| `title` | 用户可理解的任务标题 |
| `completion_criteria` | 判断任务何时真正完成的标准 |
| `status` | `pending`、`running`、`completed`、`failed` 或 `skipped` |
| `failure_reason` | 失败或跳过时的结构化原因；其他状态为空 |

任务标题必须描述子目标，不能直接写工具名。完成标准必须能被真实结果验证。

不合格示例：

```text
任务：处理项目资料
```

合格示例：

```text
任务：读取项目资料
完成标准：成功读取 workspace 中与项目相关的 Markdown 文件，并形成可用于摘要的项目内容。
```

## 计划规则

- 一份计划只能包含 2–5 个任务。
- 计划在首次工具调用前完整生成。
- 初始状态全部为 `pending`。
- 计划生成后自动开始执行，不增加整份计划审批。
- 执行期间不能新增、删除、重排任务，也不能修改标题和完成标准。
- 同一时间只能有一个任务处于 `running`。
- 一个任务可以包含多轮模型判断和多次工具调用。
- 模型提出任务完成不等于任务真实完成；状态必须由 Observation 和完成标准共同验证。

## 状态流转

正常状态只能这样变化：

```text
pending -> running -> completed
                   -> failed

pending -> skipped
```

`skipped` 只用于首次失败后尚未开始的任务。

禁止出现：

- 多个任务同时 `running`。
- `completed` 重新变回 `running`。
- `failed` 后继续执行后续任务。
- 没有真实结果就将任务标记为 `completed`。
- 为简单目标生成只有一项的计划。

## 自动执行与权限边界

任务计划生成后立即执行，因为计划本身不产生副作用。V0.8 不增加“批准整份计划”的交互。

危险动作继续沿用现有权限机制：

- `write_file` 在实际写入前请求 CLI 权限。
- `run_command` 在实际启动命令前请求 CLI 权限。
- 用户拒绝后不能出现对应的 `tool_started`。
- Trace Viewer 继续只读，不提供批准、拒绝、编辑或重新执行入口。

任务分解不能降低任何现有权限或 workspace 安全边界。

## 失败规则

V0.8 采用“首次失败即停止”：

1. 当前任务因为工具错误、模型失败、完成标准未满足或权限被拒绝而标记为 `failed`。
2. 所有尚未开始的任务从 `pending` 变为 `skipped`。
3. Agent 不自动重试、不绕过失败、不修改计划。
4. 整体运行状态为失败。
5. 最终结果必须分别说明已完成、失败和跳过的任务。

V0.8 不判断后续任务是否独立，因为这会引入任务依赖图、部分成功策略和恢复机制。

## 完整成功路径

```text
用户目标
-> Context Build
-> Model Decision(create_plan)
-> Plan Created(4 tasks)
-> Task 1 Running
-> list_dir / Observation
-> Task 1 Completed
-> Task 2 Running
-> read_file... / Observations
-> Task 2 Completed
-> Task 3 Running
-> run_command permission / execution / Observation
-> Task 3 Completed
-> Task 4 Running
-> write_file permission / execution / Observation
-> Task 4 Completed
-> Final Answer
```

每个任务内部仍然由原有 Agentic Loop 驱动，不新增第二套工具执行机制。

## 权限拒绝路径

以写文件权限被拒绝为例：

```text
Task 1 Completed
-> Task 2 Completed
-> Task 3 Completed
-> Task 4 Running
-> Permission Requested(write_file)
-> Permission Resolved(approved=false)
-> Observation Added(permission rejected)
-> Task 4 Failed
-> Final Answer(run failed)
```

如果失败发生在中间任务，所有后续任务必须标记为 `skipped`，且不能出现对应的工具启动事件。

## Trace Viewer 信息架构

### 简单目标

不展示任务计划栏，保持 V0.7 模块顺序和交互：

```text
运行状态
-> 本次任务统计
-> 原始需求
-> 最终结果
-> 执行轮次 / 轮次详情
```

### 复合目标

在最终结果与观察窗口之间增加任务计划栏：

```text
运行状态
-> 本次任务统计
-> 原始需求
-> 最终结果
-> 任务计划
-> 当前任务的执行轮次 / 轮次详情
```

任务计划栏展示：

- 整体进度，例如 `4 / 4 completed`。
- 2–5 个有序任务。
- 每个任务的标题、完成标准摘要和状态。
- 失败任务的原因。
- 后续任务为何被跳过。

点击任务后，左侧“执行轮次”只展示该任务内部的 Agentic Loop 轮次；右侧仍展示所选轮次的原始步骤详情。V0.7 已有的 Context Build、Model Decision、Permission、Tool、Observation 和原始事件信息不能被任务计划替代。

### 条件展示规则

- 存在 2–5 个任务：渲染 `#task-plan-panel`。
- 不存在计划：页面中不渲染空面板、单任务卡片或占位提示。
- 简单目标不能因为内部有多个工具调用而显示任务计划栏。

## 原型交互

完整原型必须支持：

1. 在“复合任务成功”“复合任务失败”“简单任务 V0.7”之间切换。
2. 点击任务卡片，切换该任务对应的轮次列表。
3. 点击轮次，切换右侧步骤详情。
4. 失败状态明确显示 `failed` 和 `skipped`，不能使用完成态颜色。
5. 简单任务模式隐藏整个任务计划栏并恢复 V0.7 结构。
6. 所有交互只改变静态原型展示，不执行工具、不改变真实 Agent。

## V0.8 不做

- 动态增加、删除或重排任务。
- 自动重试、恢复或重新规划。
- 并行任务。
- 嵌套子任务或任务依赖图。
- 用户在网页编辑或批准计划。
- 页面触发工具调用或重新执行。
- 多 Agent、长期记忆、MCP、Hook 或插件系统。

## 产品验收标准

V0.8 只有同时满足以下产品效果才算完成：

1. 简单目标的运行和 Trace Viewer 结构与 V0.7 一致。
2. 复合目标在首次工具调用前产生 2–5 个固定任务。
3. 任务标题和完成标准描述子目标，而不是工具名称。
4. 同一时间只有一个任务运行。
5. 一个任务可以容纳多轮模型判断和多次工具调用。
6. 任务状态由真实 Observation 驱动。
7. 首次失败后当前任务失败、后续任务跳过、整体运行失败。
8. 现有写文件和命令权限链不被绕过。
9. Trace Viewer 能从任务进入内部轮次，再查看原始步骤详情。
10. 页面不会把任务清单退化成 TraceEvent 的重复列表。
11. 真实浏览器验证页面非空、交互有效、窄屏可读且 console 无 JavaScript error。
